@AGENTS.md

## Project

**ArcRadar** — a cybersecurity intelligence and threat-monitoring platform (indicators/IOCs, IP/domain/URL/hash intelligence, vulnerabilities, an ATT&CK matrix built from alerts, alerts, investigations, reports, API keys, audit log). Holberton portfolio project. Production target: Vercel + Supabase. State, decisions and per-phase handoff notes live in `docs/ARCRADAR_PROGRESS.md`; how to run it is in `docs/LOCAL_DEVELOPMENT.md`.

Stack: Next.js 16 (App Router, `src/` layout) + TypeScript, Tailwind 4, Supabase (Postgres + Auth), Zod, Vitest. Next 16 renamed middleware to `proxy` (`src/proxy.ts`); `cookies()` is async. Read `node_modules/next/dist/docs/` before using Next APIs.

## Commands

```bash
npm run dev | build | start        # Next.js
npm run lint | typecheck | test    # typecheck runs `next typegen` first (LayoutProps etc. are generated)
npm run format | format:check      # Prettier (printWidth 100)
npx vitest run tests/env.test.ts   # single test file (or add -t "name" to filter)
npm run db:start | db:stop         # local Supabase in Docker (Docker Desktop must be running)
npm run db:reset                   # rebuild local DB from supabase/migrations + supabase/seed.sql
npm run db:test                    # SQL security/constraint tests in supabase/tests (stack must be running)
npm run db:types                   # regenerate src/types/database.ts after any schema change
npm run db:env                     # write local Supabase URL/keys into .env.local
npm run e2e                        # Playwright in real Chrome (local Supabase up + `npm run build` first); needs the built app, starts `npm start` itself
npm run check:contrast             # WCAG contrast of design tokens (run after editing colors in globals.css)
npm run apikey:create | ingest:sample   # make an ingest API key (admin sign-in from ARCRADAR_EMAIL/PASSWORD); send fictional Wazuh alerts to a running app
npm run import:mitre               # load the MITRE ATT&CK technique catalog (names and tactics for the matrix page); --url + SUPABASE_SERVICE_ROLE_KEY for a hosted project
npm run api:smoke                  # end-to-end API checks (app running + local Supabase up); SMOKE_BASE_URL=http://localhost:8080 to go through nginx
powershell -File scripts/nginx.ps1 test|start|stop|reload   # local nginx :8080 -> Next.js :3000
```

Schema change loop: `npx supabase migration new <name>` → write SQL → `npm run db:reset` → `npm run db:types` → `npm run db:test`. Never edit an applied migration; add a new one. New tables need RLS and policies in the same migration (the DB test enforces it).

Windows: `node` is not on Git Bash's PATH, and each PowerShell call starts fresh. Prefix PowerShell with `$env:Path = [Environment]::GetEnvironmentVariable('Path','Machine') + ';' + [Environment]::GetEnvironmentVariable('Path','User')`. The project sits under OneDrive: keep OneDrive stopped during installs and builds.

## Architecture (the parts that span files)

- **Layers (built in Phase 2):** Route Handler → auth/authz guard → Zod validation → service layer → repository (Supabase) / provider adapter. Export handlers wrapped in `publicRoute` / `protectedRoute({ permissions })` (`src/lib/api/handler.ts`), or `ingestRoute({ scope })` for machine endpoints (API key instead of session, no cookies): they do the origin check, session + permission guard, error mapping and the `{ success, data, error }` envelope. Throw `apiErrors.*`; use `unwrap()` around queries. Recipe and error codes: `docs/API.md`.
- **Frontend:** pages under `src/app/(app)/` are guarded by the layout (`getPageAuth()`, server-verified); `(auth)` holds the signed-out pages; `proxy.ts` only redirects cookie-less visitors. Never wrap `cookies()`/`redirect()` in a bare try/catch without `unstable_rethrow(error)`. UI is Tailwind with semantic tokens from `globals.css` (never raw hex or Tailwind palette colors), primitives in `src/components/ui/` (gallery at `/design` in dev), nav in `src/lib/nav.ts`. Error boundaries take `retry`, not `reset`, in this Next version. Every record shown to users must carry its provenance badge. Forms call the JSON API with `apiFetch`.
- **Records (indicators are the reference):** search is a SQL function called through PostgREST (never build filter strings from user input); validate per type in TypeScript and canonicalize before storing; strict Zod bodies (no `origin`, ownership or ids from clients); list pages keep their state in the URL; audit every write. Provenance is enforced in the database for every record table (indicators, vulnerabilities, events, alerts, investigations, reports: clients create only `local`, `protect_origin` blocks relabelling): give every new record table the same check, and write `external`/`demo` data only server-side. Reports (Phase 7) are generated snapshots (`content` computed once at creation from data the caller can already read) with their own search (`search_reports`); the dashboard (`/api/dashboard`) reads real, unfiltered totals plus a bounded activity window. Many-to-many link sets (investigation tags, items) are replaced by atomic SQL functions and every linked id is checked to exist before anything is written. Alerts follow a state machine (`src/lib/alerts/workflow.ts`); an investigation's status history is written by the server as `system` notes. A page past the last one must be an empty page, not an error. Details and the recipe: `docs/API.md` and the Phase 4 handoff in `docs/ARCRADAR_PROGRESS.md`.
- **Permissions:** keys live in the database (migration `20260925100100`); `src/lib/rbac/permissions.ts` mirrors them and `tests/rbac.test.ts` fails on drift. Guards are a fast check; RLS is the authority, so repositories use the caller's client (`ctx.auth.supabase`), not the admin client.
- **Audit:** `writeAuditLog()` (service role, never throws) after an authorized action; add new action names to `src/lib/audit/actions.ts`. `audit_logs` is append-only.
- **Three Supabase clients, different trust levels:** `lib/supabase/client.ts` (browser, anon key), `server.ts` (acts as the signed-in user; RLS applies; default for data access), `admin.ts` (service role; bypasses RLS; server-only; only for audit-log writes, investigation history notes, API key creation / revocation / lookup by hash, `auth.admin.listUsers()` plus a profile's role/active update, the vulnerability import and `ingest_telemetry()`, after authorization). `session.ts` + `src/proxy.ts` refresh auth cookies. Validate sessions with `auth.getUser()` for anything sensitive.
- **Authorization lives in the database.** Roles (admin / analyst / viewer), permission keys (`indicators:write`, ...) and `role_permissions` are reference data in migration `20260925100100`. RLS policies call `has_permission('<key>')`. App-side RBAC (Phase 2) must mirror those keys. Migration `20260925100500` holds all policies and column-level grants (clients cannot change `profiles.role_name`, read `api_keys.key_hash`, or write `audit_logs`).
- **Provenance:** every intel record has `origin` (`demo` | `local` | `external`). Never present demo or local data as live intelligence.
- **Provider abstraction (built in Phase 5, `src/lib/intel/`):** UI → API → service → provider interface → Demo or external provider. External providers are enabled only when their server-side key is set; the app must work with none. Live lookups are asked only for callers with `indicators:write` and never for private/reserved values or URLs with credentials; every outbound request goes through `getJson` (fixed HTTPS base, no redirects, deadline, size cap, key in a header); demo data is used only when no live provider delivered and is always labelled; nothing is ever fetched, uploaded or scanned. Vulnerabilities live in the database; external CVE data enters only via the service-only `import_external_vulnerability()`. Recipe and rules: `docs/API.md` (Intelligence lookups, Vulnerabilities) and decisions 14-16 in `docs/ARCRADAR_PROGRESS.md`.
- **Telemetry (built in Phase 6b):** real events arrive from a Windows 10 endpoint via Wazuh Agent → Wazuh Manager → `POST /api/ingest/wazuh` (the Manager pushes over HTTPS with an API key; delivery script in `deploy/wazuh/`, setup in `docs/WAZUH_INTEGRATION.md`; not yet run against a real Manager). Machine endpoints use `ingestRoute({ scope })` (`src/lib/api/ingest-route.ts`): an API key (`src/lib/api-keys/`, hash only, `ingest:wazuh` ↔ `events:write`, re-verified on every request, one `401` for every unusable key) instead of a session. Ingested rows are written only by `ingest_telemetry()`, a service-role-only SQL function (one transaction per batch, `origin = 'external'`, idempotent by `(source, source_event_id)`, indicators recorded `unknown`); Wazuh code stays behind the `TelemetrySource` adapter (`src/lib/telemetry/`), separate from enrichment providers; connector health says receiving / quiet / never, never "connected". The nodes may sit on different computers and networks, so never hard-code hosts or assume one machine or subnet. See `docs/TELEMETRY_ARCHITECTURE.md` before touching events, alerts, assets, integrations or API keys.
- **Automatic data and the ATT&CK matrix (2026-09-30, decisions 28-29 in `docs/ARCRADAR_PROGRESS.md`):** indicators, vulnerabilities and techniques no longer depend on typing, and there are **no threat actor / campaign / malware records** any more (removed at the user's request: ArcRadar is about what happens on the machines it watches, not a catalog of adversaries). (1) **Research on arrival** (`src/lib/telemetry/enrich.ts`): after a Wazuh delivery is stored, `after()` researches the new, unresearched indicators (max 4 per delivery, `indicators.researched_at` marks them; public values only; never a local/demo indicator) at the live providers and records the worst verdict through `record_external_indicators()` (service role only; a verdict only moves up). A person's live lookup records itself the same way (`src/lib/intel/record.ts`); demo answers record nothing. (2) `src/lib/feeds/` imports the free public feeds (abuse.ch URLhaus/Feodo/ThreatFox as indicators, CISA KEV as vulnerabilities) only when an admin presses Import now (`POST /api/feeds/import`, `integrations:manage`); the groups `abusech` and `cisa_kev` are integration rows an admin can pause; no cron (the user chose that). (3) Lookup providers include AlienVault OTX (`OTX_API_KEY`) and Shodan InternetDB (`SHODAN_INTERNETDB=true`, no key). (4) **MITRE**: `npm run import:mitre` loads the technique catalog (reference data); `/mitre` is an ATT&CK matrix (`src/lib/mitre/`, `mitre_observed_techniques()`): columns per tactic in attack order, techniques an alert named are colored by worst severity with an alert count and open `/alerts?technique=T…`; the dashboard shows the most-seen techniques. MISP/OpenCTI have no adapter (self-hosted servers).
- **AI and response orchestration (built in Phases 8-10, `src/lib/ai/`, `src/lib/response-actions/`, `src/lib/detection-rules/`):** ArcRadar is repositioned as an incident-response / case-management / response-orchestration platform that complements a SIEM; AI (Groq now, admin-configurable to OpenAI, Anthropic, DeepSeek or a local Ollama via `GET/PATCH /api/ai/settings`, `ai:manage`) is a third provider family next to `IntelProvider` and `TelemetrySource`, called through `postJson` (the POST counterpart of `getJson`: fixed HTTPS base, no redirects, deadline, size cap; Ollama alone may use plain http, since its base URL is a trusted server env var, never admin-UI input). An alert, investigation or indicator page can ask for one of seven analyses (`ai:use`; needs an active, configured, enabled provider; `AI_KIND_SUBJECT_TYPE` and a matching DB check constraint pin each analysis kind to exactly one subject type); every answer is validated against a zod schema, stored immutably in `ai_analyses`, shown as an "AI-generated — analyst-assisted" card next to the record's real fields, and audited. An AI "immediate response actions" answer can seed the `response_actions` catalog (provenance-protected like other curated reference data) with tracked `response_action_log` rows an analyst moves by hand through `recommended → acknowledged/completed/skipped` (no backwards move once terminal), currently wired up for alerts only; an AI "investigation checklist" answer seeds `investigation_checklist_items` an analyst can also add/check/remove by hand; an AI "verdict recommendation" on an indicator is applied only as a normal, audited indicator edit, never automatically. It only ever recommends and tracks — never executes anything automatically. **Alert deduplication and custom detection rules (Phase 10)**: one `before insert` trigger on `alerts` (`alerts_dedup_and_rules`) does both, inline, for every alert however it is created (ingest or manual) — no background worker. `detection_rules` (`rules:manage`, admin only) is a fixed, closed condition grammar (6 field/op pairs; `detection_rule_matches()` fails closed on anything else) that can only raise a matching alert's severity and trace itself (`matched_rule_id`), never lower it or add a tag. A repeat alert (same source/title/asset/indicator, a still-open primary, within 60 minutes) links as a duplicate (`duplicate_of`, the primary's `duplicate_count`) instead of opening a fresh row; `GET /api/alerts` hides a duplicate by default (`?duplicates=show` reveals it) and every alert-count aggregate excludes it. See `docs/AI_AND_ORCHESTRATION_ARCHITECTURE.md` before touching any of it.
- **Wazuh detection rules as code (2026-09-30, decision 30 in `docs/ARCRADAR_PROGRESS.md`, `docs/WAZUH_RULES.md`):** `/detection-rules` has two tabs: "Wazuh rules" (new) and "Severity rules" (the Phase 10 `detection_rules`, unchanged). A Wazuh rule (`wazuh_rules`, admin `rules:manage`) is stored as structured fields and ArcRadar **renders the XML itself** (`src/lib/wazuh-rules/xml.ts`), so an active response or command can never be in it; a person writes it or the AI drafts it (`POST /api/wazuh-rules/generate`, same zod checks, regex guard), then Send to GitHub (commits `rules/arcradar_<id>.xml` through `src/lib/github/contents.ts`, env `GITHUB_TOKEN`/`GITHUB_RULES_REPO`/`GITHUB_RULES_BRANCH`), Edit or Reject. ArcRadar never reaches the Manager: `deploy/wazuh/apply-arcradar-rules.sh` on the Manager pulls the repository, refuses unexpected elements, installs only `arcradar_<id>.xml`, tests with `wazuh-analysisd -t`, rolls back on refusal. Draft → pushed / rejected; a pushed rule cannot be deleted. A rule may be a repeating one (`frequency`/`timeframe`/`same_fields`, migration `20260930160000`). The Manager runs the script from cron every 10 minutes. Nothing executes.
- **Security hardening (Phase 11, `src/lib/rate-limit/`, `src/lib/security/csp.ts`):** rate limiting is a shared, Postgres-backed fixed-window counter (`check_rate_limit()`, service-role only — decision 1 rules out in-memory state or a second store) wired into `publicRoute`/`protectedRoute`/`ingestRoute` as an optional `rateLimit`, checked once the caller is known and before the handler runs, fails open on an infrastructure error; covers the auth endpoints (IP-keyed), every AI-calling endpoint (caller-keyed), manual alert creation and ingestion (caller-/key-keyed — both run the dedup/detection-rule trigger). Session cookies are `httpOnly` and, in production, `secure` (`src/lib/supabase/cookie-options.ts`; the browser Supabase client is never imported anywhere, so nothing needs JS access to the cookie). Every response carries a nonce-based Content-Security-Policy with no `unsafe-inline` (`src/proxy.ts` generates the nonce; static headers — `X-Frame-Options`, `X-Content-Type-Options`, `Referrer-Policy`, `Permissions-Policy`, production-only HSTS — are in `next.config.ts`). The outbound paths (`getJson`, `postJson`) were SSRF-reviewed: every base URL is a literal or a server env var, never DB/admin input, and a dynamic value only ever becomes a percent-encoded path segment or query value, never a host.
- **Env:** `lib/env/public.ts` reads `process.env.NEXT_PUBLIC_*` literally (required for Next to inline them); `lib/env/server.ts` is `server-only`. Never import server env or the admin client from a Client Component.
- **Seed:** `supabase/seed.sql` is local-only demo data (including demo users) and uses `pg_temp` lookup helpers. It never runs on `supabase db push`.

## Phased workflow (important)

The project follows the phase plan in `docs/ARCRADAR_PROGRESS.md` (Phases 0–12).

- Read `docs/ARCRADAR_PROGRESS.md` first in every session.
- Execute **one phase only**, and only after the user explicitly says to continue with that phase (for example `CONTINUE PHASE 2`, or a clear "continue" in reply to your prompt asking for it). Never chain phases, and never treat "keep going" as permission to start the next one.
- A phase ends with: validation run, progress file updated, a concise report (completed, files changed, validation, limitations, next phase), then STOP.
- The full product spec is the user's original meta prompt, saved verbatim in `docs/ORIGINAL_PROMPT.md` (read it when a phase needs details not captured in the progress file). `docs/HANDOFF_PROMPT.md` is a ready-to-paste prompt for starting a fresh Claude Code session on this project.

## Constraints that shape every decision

- Production is Vercel + Supabase. No always-on server, no local filesystem persistence, no in-memory cross-request state, no background worker, no second database. nginx is local-only.
- Supabase service-role key and external provider keys are server-only. Never expose them to client code. Never commit secrets; keep `.env.example` current.
- Authorization must be enforced server-side and in RLS, not only in the UI.
- Do not deploy, and do not access the user's Vercel or Supabase accounts.

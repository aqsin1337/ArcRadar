## Architecture decisions

1. **Deployment:** Vercel (app + API) + Supabase (Postgres, Auth). No always-on server, no local-FS persistence, no in-memory cross-request state, no background worker. nginx is a **local-only** reverse proxy (`deploy/nginx/`, `scripts/nginx.ps1`, port 8080 to 3000); Vercel never depends on it.
2. **Backend layering (built in Phase 2):** Route Handler (`publicRoute` / `protectedRoute` wrapper) → auth/authz guard → Zod validation → service layer → repository (Supabase) / provider adapter. Response envelope `{ success, data, error }`; conventions, error codes and the "add an endpoint" recipe are in `docs/API.md`.
3. **Supabase clients:** `lib/supabase/client.ts` (browser), `server.ts` (user-scoped, RLS applies), `admin.ts` (service role, bypasses RLS, server-only), `session.ts` + `src/proxy.ts` (refresh auth cookies and redirect cookie-less visitors to `/login?next=`, an optimistic shortcut only; API routes and the `(app)` layout do the real checks). Use the user-scoped client by default; the admin client only for audit-log writes, API key creation, revocation and lookup by hash, admin user management, investigation history notes (decision 18), the vulnerability import (decision 15) and `ingest_telemetry()` (decision 19), after authorization.
4. **Env handling:** `lib/env/public.ts` (NEXT_PUBLIC_*, literal `process.env` reads so Next can inline them), `lib/env/server.ts` (`server-only`, service-role key + optional provider keys; empty means not configured). Errors list variable names, never values. `.env.example` documents everything; `.env.local` is generated by `npm run db:env`.
5. **Provider abstraction:** interfaces per domain with a Demo provider as default and optional external adapters enabled only when their key is set. The app works with zero external keys. UI never calls external APIs directly. Records carry `origin` (demo / local / external) and the UI must label it.
6. **RBAC in the database:** roles (`admin`, `analyst`, `viewer`), permission keys such as `indicators:write`, and `role_permissions` are reference data in migration `20260925100100`. RLS policies call `has_permission('<key>')`; `current_role_name()` resolves the caller's role from `profiles`. Analysts can read everything, write indicators / alerts / investigations / reports, and manage their own API keys; only admins delete indicators, alerts and investigations, edit threat intel and vulnerabilities, manage integrations, read the audit log. Viewers are read-only.
7. **Security controls in the schema:** RLS on all 32 public tables (111 policies); `anon` has no table access; clients cannot TRUNCATE; `profiles` clients may only update `display_name` and `avatar_url` (so no self-promotion); new users are always `viewer` (role never read from signup metadata); `created_by` defaults to `auth.uid()`, must equal the caller on insert, and cannot change afterwards; `api_keys` store only a SHA-256 hash and clients cannot read `key_hash` or write at all; `audit_logs` is append-only (trigger blocks update, delete, truncate even for the owner), written only by the service role, and has no FK to users so the trail survives user deletion; indicators are structurally validated in the database (`is_valid_indicator`, unique per type + normalized value).
8. **Testing:** Vitest for app code (`tests/`), plain-SQL security tests for the database (`supabase/tests/`, run with `npm run db:test`), `npm run api:smoke` for end-to-end API checks against the running app + local stack, and Playwright (`npm run e2e`, real Chrome, `tests/e2e/`) for the UI.
9. **Auth model (Phase 2):** Supabase Auth owns identity; the app never stores passwords. Server code calls `requireAuth()` (`getUser()` against the auth server, then the profile through RLS: a missing row means disabled). The permission check in `protectedRoute` is a fast mirror (`src/lib/rbac`); RLS remains the authority. Audit writes are best-effort (`writeAuditLog` never throws, returns `false` and logs on failure) and go through the service role. Sign-in, sign-up and recovery answers are enumeration-safe.
10. **API JSON is snake_case** (rows are returned as the database has them, so `Row<...>` types are shared with the UI).
11. **Telemetry source (requirement added 2026-09-26):** real telemetry comes from a Windows 10 machine with a Wazuh Agent → a Wazuh Manager (Linux-only) → ArcRadar. The three roles may run on different computers and networks (main computer: ArcRadar; the user's two other computers: Windows 10 and the Manager, split not decided). Rules: topology-independent configuration only, the Manager **pushes** alerts to an ArcRadar ingest endpoint over HTTPS with an API key (no polling of Wazuh from ArcRadar, no Wazuh credentials stored, remote nodes never touch Supabase), telemetry sources are separate from enrichment providers, provenance is always labelled. Built in Phase 6b (decisions 17 and 19); design and open questions in `docs/TELEMETRY_ARCHITECTURE.md`, Manager setup in `docs/WAZUH_INTEGRATION.md`.
12. **Frontend (Phase 3):** server-verified page guard (`getPageAuth()` in `src/lib/auth/session.ts`: `getUser()` + profile through RLS, statuses `ok | signed_out | disabled | unavailable`, cached per request) used by the `(app)` layout, which shows dedicated screens for disabled and unavailable states. Never catch Next's control-flow errors: `getPageAuth` and `publicRoute`/`protectedRoute` call `unstable_rethrow` first (a swallowed `cookies()` signal was a real bug caught by the build). Forms are thin clients of the JSON API (`src/lib/api/client.ts`), validated in the browser with the same Zod schemas. Design system: CSS tokens in `src/app/globals.css` (dark default, light via `data-theme` set on the server from a cookie, so no flash), hand-written primitives in `src/components/ui/`, contrast enforced by `npm run check:contrast`. Navigation lives in `src/lib/nav.ts` (`live` vs `soon` items, hidden by permission). `/design` is a dev-only component gallery. The sign-in page can offer one-click demo accounts only when `NEXT_PUBLIC_DEMO_LOGINS=true` (set by `npm run db:env`); the credentials come from a server-only module so they are never in the shipped JavaScript.
13. **Indicators (Phase 4):** text search is a SQL function (`search_indicators`, `security invoker`, escaped `ILIKE`, every word must match value, description, source or a tag) called through PostgREST, which adds filters, sorting (stable tie-break on `id`), `count` and `range`; nothing user-typed is ever built into a filter string. Values are validated per type in TypeScript (mirror of `is_valid_indicator`, compared against the database) and canonicalized before storage; a duplicate is a `409` naming the existing record. **Provenance is enforced by the database**: clients can only create `local` indicators and cannot relabel one (external and demo data come from server-side writes). The list page keeps all state in the URL (server-rendered, shareable, back button works); columns collapse with container queries and the badges (including origin) move under the value on phones. Global search is a combobox over `GET /api/search`, built to gain one source per record type.
14. **Intelligence lookups (Phase 5):** `src/lib/intel/`. One vocabulary for every provider: an `IntelProvider` implements the lookups it can answer (`lookupIp/Domain/Url/Hash`), returns a normalized profile (reputation, engine counts, findings, kind-specific facts) or `null` ("no record"), or throws a `ProviderError` (`auth | rate_limited | timeout | unavailable | bad_response`). The service (`lookupIntel`) asks the live providers in parallel under one deadline, records an attempt per provider (`ok | not_found | skipped | failed`) and falls back to the **demo provider** only when no live provider delivered; results of different providers are never blended and every card carries its own origin label. Live providers (VirusTotal for IP/domain/URL/hash, AbuseIPDB for IP) exist only when their server-side key is set, are asked only for callers with `indicators:write` (a self-registered viewer must not spend the quota), and never receive private, reserved or documentation addresses, reserved names, or URLs with credentials (`externalSkipReason`, so internal addressing does not leak). All outbound traffic goes through `getJson` (`src/lib/intel/http.ts`): fixed HTTPS base address per provider, path built from encoded segments and re-checked against the base origin, no redirects, deadline, 2 MB cap, key in a header, errors without bodies or keys. Nothing is ever fetched, uploaded or scanned (VirusTotal is only asked what it already knows; a URL is looked up by its base64url id). Verdicts are conservative (no detections is `unknown`, never `benign`). A lookup that contacts a live provider writes one `intel.lookup` audit entry; demo lookups write none. The demo dataset (`providers/demo-data.ts`) is fictional and lines up with the seed (a test compares them), invents no location or attribution, and adds only three harmless real subjects (8.8.8.8, example.com, the EICAR test file, kept as digests because antivirus flags the string). The workspace side (`local.ts`, `timeline.ts`) adds the tracked indicator with relationships and links, other indicators that mention the subject, and alerts, events and investigations of that indicator as a merged timeline. Pages are server components under `/intelligence/[kind]` with the value in the address (`?q=`); values of another kind get a suggestion link (`detectKind`).
15. **Vulnerabilities (Phase 5):** the database is the store (demo seed, local, external); pages and API read it with the caller's client. Text search is `search_vulnerabilities` (`security invoker`, escaped `ILIKE` over CVE id, title, description, affected vendor and product), statistics are `vulnerability_severity_counts`. **Provenance is enforced in the database as for indicators**: clients can only create `local` records and cannot relabel one (`vulnerabilities_protect_origin`, the insert policy). External data enters only through `import_external_vulnerability()`, a `security definer` function callable by the service role alone, which the app calls after authorizing an administrator (`vulnerabilities:write`); it never replaces a demo or local record. NVD is the (optional, key-gated) `VulnerabilityProvider`; NVD answers a rejected key with 404 plus a `message` header, which the adapter reports as an auth failure rather than "no such CVE" (found by trying a fake key against the real service). A CVE NVD has not scored is `info` with no score, never a guess; `exploited_in_wild` only when CISA lists it. Reference links are rendered only for http(s) URLs.
16. **Shared list UI (Phase 5):** `ListFilters` (URL-driven search, filter menus and sort menu; `IndicatorFilters` and `VulnerabilityFilters` are thin configurations of it), `SortHeader`, `DetailRow`/`TimeText`, `ProvenanceNotice`, `parseListParams`/`blankToUndefined` (`src/lib/validation/query.ts`). Global search gained the vulnerability source and, when the text is structurally an IP, domain, URL or hash, a first "Look up" group (an action with no origin badge that claims nothing about the value).

18. **Alerts, investigations and threat intelligence (Phase 6):** (a) **Provenance now protects every record table**: threat actors, campaigns, malware, events, alerts and investigations get the same insert policy (`origin = 'local'`, `created_by` is the caller) and `protect_origin` trigger as indicators; external data will come only from server-side writes. (b) **The alert lifecycle is a pure state machine** (`src/lib/alerts/workflow.ts`): `new` can go anywhere forward, `acknowledged` to investigating / resolved / false positive, `investigating` to resolved / false positive, a closed alert can only reopen into `investigating`. The server works out `acknowledged_at` and `resolved_at` in one place (the database requires `resolved_at` exactly when closed), takes an unassigned alert for the analyst who moves it out of `new`, and applies the update only while the alert is still in the status the caller saw (`409` for a concurrent change). The UI offers only the moves the lifecycle allows, and the server checks again. Only active people who hold `alerts:write` can be assigned an alert. (c) **An investigation's history is written by the server**: a status, priority or analyst change adds a `system` note with the **service role** (an additional use of the admin client, after authorization, best effort: failing to write it never undoes the change); row level security lets clients write only `note`-kind rows and only their own, an administrator may remove another person's ordinary note, and nobody can edit or delete the history. The timeline is built from what is recorded (notes, history, evidence, attachments and their timestamps), not from a separate event log. (d) **Attaching an alert to an investigation starts work on it**: a `new` or `acknowledged` alert moves to `investigating` through the same lifecycle rules and audit entry (`reason: "attached to an investigation"`); a closed alert is left alone. (e) **Threat intelligence is curated by administrators only** (analysts read it); created records are `local`; names are unique ignoring case; ATT&CK techniques are public reference data, read-only in the UI and API and therefore without an `origin` (they show no provenance label and say they are reference data). (f) **Link sets are replaced atomically** by SQL functions (`null` leaves a set alone, an empty array clears it) and the service checks that every linked id exists **before writing anything**, so a bad link never leaves a half-saved change; creating a record whose linking still fails removes the record again. (g) Search for every new record type is a `security invoker` SQL function with ANDed terms and literal wildcards, and every match is wrapped in `coalesce(..., false)`: a NULL column made `NOT (... OR NULL)` NULL and the record matched every search (found while testing, also present in Phase 4's `search_indicators`; fixed in the same migration, regression-tested in `indicators.test.sql` and `operations.test.sql`). (h) Indicators can now be linked to actors, campaigns and malware and related to each other from the indicator page (`PUT .../links`, `POST/DELETE .../relationships`): the limitation recorded in Phases 4 and 5. (i) Global search gained eight sources, each searching with the same schema and repository as its list page; a hit may carry `mono` (values read better in monospace). (j) Administrators can delete alerts and investigations from their pages behind a confirmation (`DeleteRecordButton`, shared with threat intelligence).

19. **Telemetry ingestion (Phase 6b):** (a) **API keys** (`src/lib/api-keys/`): `arc_` + 43 URL-safe characters from 32 random bytes; only the SHA-256 hash and an 8-character prefix are stored and the key is shown once; the scope `ingest:wazuh` maps to the permission `events:write` (administrators); a key is re-verified on **every** request (well formed, known, not revoked or expired, owner active and still holding the permission, scope present), every reason a key is unusable is one `401` (a valid key without the scope is `403`), `last_used_at` is refreshed at most once a minute, a person holds at most ten usable keys. (b) **`ingestRoute({ scope })`** (`src/lib/api/ingest-route.ts`) is the third route wrapper next to `publicRoute` and `protectedRoute`: a key instead of a session, no cookies and so no same-origin check, no user-scoped Supabase client, the same envelope and `unstable_rethrow`; `src/proxy.ts` leaves `api/ingest/` alone. (c) **Storage is one service-role-only SQL function**, `ingest_telemetry(source, records)` (`security definer`, `search_path = ''`, execute revoked from `public`, `anon` and `authenticated`): one transaction per batch (all or nothing), idempotent through a unique `(source, source_event_id)` on external events and alerts (`source_event_id` is `<manager name>:<alert id>`; a known event is counted as a duplicate and skipped before it can reach the alert), the asset is upserted (`last_seen` never moves back, `first_seen` never forward), indicators are recorded `external` with the verdict `unknown` (an indicator somebody already tracks is linked, never changed; a value the database refuses is skipped instead of failing the batch), and `integrations.last_sync_at` is set. The app calls it with the admin client after the key is verified: an additional, narrow use of the admin client, listed with the others in decision 3. (d) **The Wazuh adapter is a `TelemetrySource`** (`src/lib/telemetry/`), separate from `IntelProvider`: every usable alert is an event, a rule level of 7 or more (`ALERT_MIN_LEVEL`) is also an alert, severity comes from the level band, ATT&CK ids are kept (at most 20), the agent becomes the asset, up to five indicators are taken from a level-7+ alert (public or documentation addresses, hashes, domains, URLs; never private addresses or internal names), the raw alert is kept bounded to 16 KiB (raw log line first). An alert that cannot be used is rejected alone and listed in the response; a database refusal of the whole batch is a `422`. (e) **Connector health is honest**: `receiving` (a delivery within 15 minutes), `quiet`, `never`, `demo`; nothing says "connected" because ArcRadar cannot see a sensor, and demo feeds are labelled and never count as receiving (`telemetry_source_health()` plus `buildSourceCards`). (f) **The Manager side** (`deploy/wazuh/`) is a POSIX `sh` + `curl` script with a write-ahead spool (a switched-off ArcRadar or Manager loses nothing), retry, and requests ArcRadar refuses for good set aside; plain `http` is accepted only for localhost and Tailscale addresses and warned about elsewhere. It has **not** been run against a real Wazuh Manager. (g) Alerts gained `asset_id` and `technique_ids`, alert search also matches the asset's name and address, and the alert page shows the machine, the techniques and an external-origin notice. (h) The API-key management page was built in Phase 7; `npm run apikey:create` and `npm run ingest:sample` remain as scripted alternatives.

20. **Dashboard, reports and administration (Phase 7):** (a) **The Overview page is a real, dynamic dashboard**: headline counts (indicators by verdict, active alerts, critical vulnerabilities, open investigations, events/alerts in the selected window) are the workspace's true, unfiltered totals; `?days` (1-90, default 14) bounds the activity chart and the "recent" panels, `?severity` narrows the recent alerts and indicators panels; charts (severity distribution, IOC type distribution, indicator verdicts, an alerts-vs-events trend line) are hand-drawn SVG/CSS, colored by the same tone mapping as the record badges (`SEVERITY_TONES`/`VERDICT_TONES`, now exported from `domain-badges.tsx`) so a color means the same thing everywhere; every chart has a plain-text fallback (a data table for the trend line, numeric labels on every bar) since color is never the only signal. `GET /api/dashboard` exposes the same data for API consumers and `api:smoke`; the page itself calls the service directly, like every other list page. (b) **Reports are generated snapshots**, not a live view: `POST /api/reports` computes `content` once, from data the caller can already read, and stores it immutably; the five types are `indicators`/`alerts`/`vulnerabilities` (workspace-wide, no date range, matching the dashboard's own "current state" philosophy) and `investigation`/`threat_actor` (one record, needs its id). Reports get the same provenance protection as every other record table (`origin = 'local'` insert check + `protect_origin`, closing a gap that had existed in the schema since Phase 1 but was never exercised) and their own text search (`search_reports`, title only). A print button hides the app shell (`print:hidden` on the sidebar and header, `print:block` on the shell grid) and lets the browser's own print-to-PDF stand in for a dedicated PDF library. (c) **API keys got their management page** on top of the Phase 6b backend: create (scope choices limited to what the caller's role may issue), list, revoke, the key shown once in a dialog with a copy button. (d) **Integrations gained a real, audited switch**: `integrations.enabled` (a column that existed since Phase 1 but nothing read) now gates a live provider a second time, after its server-side key: `GET /api/intel/:kind` and `POST /api/vulnerabilities/import` both check it (a route-level check that reuses the existing, untouched `LookupDeps`/`ImportDeps` injection points, so the heavily-tested Phase 5 internals were never touched) and the existing "provider not connected" paths cover the disabled case too. The demo provider can never be turned off. (e) **User management**: `GET/PATCH /api/users` read `auth.users` through the service role (the only way to see another person's email) joined with each profile; changing a role or active flag never targets the caller's own account and never leaves zero active administrators. (f) **A real UI bug class was found and fixed three times**: a controlled checkbox or `<select>` whose value only updates in an `onSuccess` callback (after the network round trip) gets silently reverted by React's own re-render before the user's click can be observed — the API-key list, the integrations switch and the user-management table all needed an **optimistic** local update (flip the value immediately, revert on failure) instead. (g) The header's identity block is now a link to a new `/profile` page (display name, avatar URL, password change); every role can reach it, unlike the admin-only `/settings` (renamed in meaning to "workspace administration": the user list).

22. **AI integration foundation (Phase 8, 2026-09-27).** `src/lib/ai/` mirrors `src/lib/intel/` exactly: `types.ts` (the `AiProvider` interface, the 5 analysis kinds, the 5 provider ids), `http.ts` (`postJson`, the POST counterpart of `getJson`: fixed HTTPS base, no redirects, deadline, 2 MB cap, key in a header — plus one deliberate, narrow exception, `allowInsecure`, used only by the Ollama adapter, whose base URL is a trusted server env var rather than user input), `registry.ts` (one entry per configured key/URL), `prompts.ts` (versioned templates, `AI_PROMPT_VERSION`), `schemas.ts` (the zod shape per kind, doubling as the TypeScript types), `service.ts` (`getAiAvailability`, `setAiAvailability`, `generateAlertAnalysis`, `listAlertAnalyses`), `providers/{groq,openai,deepseek}.ts` (share one OpenAI-compatible request builder in `providers/common.ts`), `anthropic.ts` (its own Messages API shape), `ollama.ts` (local, `format: "json"`). 6. **A controlled input bound to server-refreshed state must update its own local state optimistically on the very click that changes it**, or the click is silently reverted before anyone sees it — found and fixed four times now (Phase 7's API keys/integrations/users, Phase 9's checklist checkbox). A plain button has no such problem (nothing in the browser changes its state on click), only a checkbox, radio or `<select>` whose `checked`/`value` is bound to a prop from the server does.

## Known limitations

- **No AI provider has ever been run with a real key** (none exist on this machine): Groq, OpenAI, Anthropic and DeepSeek's request-building and response-parsing follow each provider's published API shape and are unit-tested against fixtures, but never against the real service, not even with a fake key the way Phase 5's intel providers were (there is no free "reject a fake key and see the error" check for a chat-completion endpoint the way a lookup endpoint has one). **Ollama has no adapter test against a real server at all** — no local model server exists in this lab — and its default model name (`llama3.1`) is a guess. Try a real key (and, for Ollama, a real local server) before relying on any of the five; expect to adjust field mappings, default models and token budgets (`AI_MAX_OUTPUT_TOKENS` in `src/lib/ai/prompts.ts`).
- **AI features have a flat, non-configurable rate limit** (`aiByUser`, 30 analyses per caller per hour, Phase 11) on top of the existing role gate (`ai:use`), but nothing finer: no per-provider budget, no daily cap, no way for an administrator to raise or lower it. A portfolio project on a provider's free tier can still exhaust its quota within that hourly allowance. Finer cost control remains an open question in `docs/AI_AND_ORCHESTRATION_ARCHITECTURE.md`.
- **The active AI model is a free-text field**, not a per-provider dropdown of known models (model catalogs change often and vary per provider); a typo is only caught when the provider itself rejects the request, surfacing as a plain `503`.
- **AI analyses can drift from the alert they describe**: an analysis is an immutable snapshot of what was asked and answered at that moment (like a report), so an alert edited afterwards (a different severity, a new indicator) does not invalidate or regenerate an existing analysis; the UI shows "AI-generated — analyst-assisted", never a live-computed value, but does not warn that a specific analysis may now be stale. Re-running a kind is the only way to get an up-to-date answer.
- **Immediate response actions (the `response_actions` analysis kind) are shown only as a read-only card in Phase 8** — they are not yet turned into tracked, individually-actionable rows (`response_action_log`, Phase 9), so there is nowhere yet to mark one acknowledged, completed or skipped.
- **Live providers were never run with valid keys** (none exist on this machine): VirusTotal, AbuseIPDB and NVD parsing follows the documented response shapes and is tested against fixtures; the request path, error mapping and fallback were exercised against the real services with fake keys. Try a real key before relying on them, and expect to adjust field mappings.
- **No caching and no application-level rate limit for live lookups** (`GET /api/intel/:kind`): Phase 11's rate limiting covers auth, AI calls, manual alert creation and ingestion, but deliberately not this endpoint (it was not named in the original scope and a live lookup already costs nothing to ArcRadar itself the way an AI call does) — every lookup by an analyst or administrator still makes provider calls (VirusTotal's free tier is 4 per minute). A provider's own limit shows as `failed (rate_limited)` and falls back to demo data. Caching in Supabase (with a "last updated" per record) and a rate limit here are still open.
- Demo data has coverage for the fictional scenario only; anything else is "no record" (honest, but a portfolio visitor typing a random IP sees an empty result). The seeded CVEs are all high or critical, so the Medium, Low and Info statistic tiles show 0 until other records exist.
- Lookup providers: VirusTotal, AbuseIPDB, AlienVault OTX and Shodan InternetDB (plus NVD for CVE import); MISP and OpenCTI have no adapter (they are self-hosted servers, see decision 28). OTX and the URL/domain/hash paths of the new providers were tested against fixtures only, never with a real key (a URL is sent to OTX as one percent-encoded path segment; confirm OTX accepts that with a real key). VirusTotal profiles have no related domains for an IP (that needs a second request).
- Vulnerabilities cannot be created or edited by hand yet (list, detail, statistics and the NVD import exist); the admin write policy remains, restricted to `local` records.
- Lookup timeline entries link to alerts and investigations; events have no page of their own yet (they are listed on the Telemetry page, and an alert shows its event's raw data). The Reports module (Phase 7) can now summarize an investigation, but lookup pages do not yet offer "generate a report" directly; the workspace context still shows alerts, events and investigations inline.
- Demo indicators seeded in one statement share the same `last_seen` (the seed's `now()`), and list ties break on the random UUID, so the order of tied rows changes with every `db:reset`. Tests must not assert on tie order (the global-search E2E test used to and was fixed on 2026-09-26).
- Text search uses `ILIKE` with a trigram index on the value only; it is fine for thousands of rows. Beyond that, add a generated `tsvector` or trigram indexes on description and tag names. Results are ordered by the chosen sort, not by relevance.
- IPv4 and IPv6 values sort as text (`10.x` before `2.x`), not numerically.
- `create` is two calls (insert, then `set_indicator_tags`): if the tag step failed after the insert, the indicator exists without tags and a retry answers `409` naming it. Tag replacement itself is atomic.
- **Alerts come from three places**: the demo seed, people (local), and sensors (ingestion, external). Only alert status is protected against concurrent edits (a `409` when somebody else moved it first); investigations, threat intelligence and indicators are last-write-wins.
- An investigation's timeline is built from what is recorded (notes, the status / priority / analyst history, evidence, attachments and their timestamps). There is no change history for an alert beyond its own timestamps, and note text and evidence locations are deliberately not copied into the audit trail (only ids and evidence titles).
- Evidence is a **reference** (a link, hash, ticket number or path); nothing is uploaded, fetched or scanned, and there are no file attachments.
- Threat intelligence is entered by hand by administrators, or loaded from MITRE ATT&CK with `npm run import:mitre` (a script, not an app feature, decision 28); there is no STIX / MISP / OpenCTI import beyond that, and techniques cannot be edited through the app. Aliases, industries, countries and platforms are typed as comma-separated lists. Linked indicators on an actor, campaign or malware page show the first 25 alphabetically (with the total); the indicator list cannot be filtered by actor, campaign or family yet. Changing only the links of a record does not bump its `updated_at`.
- Date fields in forms use the browser's local time while pages show UTC (see the handoff notes), so a form can show a different clock time than the detail page.
- Deleting an actor, campaign or malware family removes only its links; there is no soft delete or undo, and only the confirmation dialog stands between a click and the deletion. Administrators can edit and delete demo records (they can never relabel them).
- Only an ordinary note's author can edit it (an administrator can remove but not edit someone else's note). The "(edited)" mark on a note is derived from `updated_at` differing from `created_at`.
- Search over alerts, investigations and threat intelligence uses unindexed `ILIKE` like indicators (fine for thousands of rows; results follow the chosen sort, not relevance).
- **A CSP nonce needs a dynamically-rendered page** (Phase 11, decision 25): every page in this app already is (the root layout reads a cookie for the theme, which forces the whole tree dynamic), so this is a note for the future, not a live gap — if a page is ever changed to opt out of dynamic rendering, its inline framework scripts and styles would stop getting a nonce and a real browser would block them (Vitest/jsdom would not notice; only the E2E/axe suite, which runs in real Chrome, would).
- An axe pass exists (`tests/e2e/accessibility.spec.ts`, Phase 11) over every list page, every create form, one detail page per record type, the mobile drawer and the signed-out pages, with zero violations found — but it is not exhaustive: every other detail page, every edit form, and the print view have not been scanned individually, and no screen reader has been tried by hand.
- The unavailable-service screen is not covered by E2E; the mapping to it is unit tested.
- The proxy runs `getClaims()` and the guard runs `getUser()`, so a guarded request makes two auth-server round trips. Fine now; revisit in Phase 8 if latency matters.
- **Telemetry ingestion was not run against a real Wazuh Manager** (none exists on this machine): the adapter follows the documented alert JSON and recorded shapes, and the delivery script was exercised with `curl` from a POSIX shell (delivery, an unreachable server and recovery, a refused key, invalid JSON, the spool cap), not from a Manager's integrator. Confirm the Wazuh version, that the alert file holds one JSON object per line, and that the Manager has `curl`; expect to adjust small things on first contact (`docs/WAZUH_INTEGRATION.md`).
- **The API-key management page exists** (`/api-keys`, Phase 7); the ingest endpoint now also carries a rate limit (`ingestByKey`, 120 batches per key per minute, Phase 11), but most other write endpoints still have none — a leaked key can still be revoked at once and a revoked key stops working on the next request, which remains the fastest mitigation. Keys are bearer secrets: reach the endpoint over HTTPS (the delivery script warns about plain `http` outside localhost and Tailscale).
- **Ingested data is stored as received, bounded**: the raw alert (up to 16 KiB, including the raw log line, which can hold user names, host names and addresses) is kept with the event and shown on the alert page to anyone with `alerts:read`. There is no retention job (Wazuh is chatty; watch the size of `events` on a free tier), no alert correlation or grouping beyond the alert id (the same rule firing twice is two alerts), and no automatic enrichment of ingested indicators (their verdict is `unknown` until an analyst looks them up).
- The asset's operating system is inferred only for Windows event data; the address is the agent's own address as Wazuh reports it. An asset is one agent id per source: re-enrolling an agent under a new id makes a new asset. The 15-minute "receiving" window is a constant (`RECEIVING_WITHIN_MINUTES`).
- `writeAuditLog` is best-effort: if the audit backend is down, requests still succeed and the failure is only logged.
- Sign-up is open by default (new users are read-only viewers). Turn it off in the Supabase dashboard for an invite-only deployment.
- The hosted Supabase project has never been exercised; only the local stack. Demo credentials are public and exist only in the local seed. `docs/DEPLOYMENT.md` (Phase 12) is the guide for the trial deployment, written but not yet run against a real hosted project.
- **No public landing page.** Resolved 2026-09-30 (decision 27): `/` is now a static landing page for signed-out visitors.
- **Reports are a snapshot with no PDF library**: the print button opens the browser's own print dialog ("save as PDF" is a browser feature, not app code), which satisfies the spec's fallback ("print-friendly ... ready for future PDF generation") without a new dependency, but there is no server-rendered PDF. A report cannot be edited or regenerated in place — a fresh one is a new row — and reports are not yet a global-search source. The three workspace-wide report types have no date range (they summarize the current state, like the dashboard); an investigation or threat-actor report needs that record's id, found by searching the type-appropriate picker in the form.
- **The dashboard's charts are hand-drawn** (SVG polylines and CSS width bars), not a charting library: adequate at this data volume, but there is no zooming, brushing or per-point tooltip beyond the activity chart's "view as a table" fallback. The severity/verdict/type distributions and the activity trend read the workspace's current data on every request; there is no caching, so a very large workspace would make the Overview page slower (fine at portfolio scale).
- **`integrations.enabled` gates the intel and vulnerability-import providers, not the Wazuh ingest endpoint.** Disabling `wazuh` on the Integrations page changes nothing about `POST /api/ingest/wazuh`; the only way to stop a Wazuh Manager today is to revoke its API key (now backed by a rate limit too, Phase 11). Wiring ingestion to the same switch would mean touching the heavily mutation-tested `ingest_telemetry()` function, deliberately left alone every phase since; still a real, open gap.
- **User management has no page-level test for the "last active administrator" rule** (it is unit-tested in `tests/users-admin.test.ts` with a mocked repository); doing it in E2E or smoke would mean demoting/reactivating a real account, which was judged too risky to script against the shared demo admin.
- The local Supabase containers are stopped at the end of a session to free RAM: run `npm run db:start` first.
